### AEM Importer → Bulk Import → Experience Catalyst の系譜図

#### 1. 一目でわかる系譜

```text
AEM Importer
  ↓
  ├─ もともとはローカル実行の開発者向け importer
  │   - import.js を作る
  │   - 単一ページを試す
  │   - 小〜中規模の bulk 実行も可能
  │   - crawl / inspect / preview を支援
  │
  └─ 課題:
      大量ページをローカル PC で回すには限界
      ジョブ管理・履歴・認証・分析・大規模処理が弱い

        ↓ 発展

Bulk Import / Import as a Service (IaaS)
  ↓
  ├─ AEM Importer の "bulk" をサービス化・大規模化
  │   - Spacecat 側で import job を実行
  │   - 大量 URL を安定処理
  │   - job status / download / queue / API を提供
  │   - UI から bulk import を扱いやすくする方向
  │
  ├─ 公開上は "Bulk Importer Tool" として見える場面がある
  │   - 非 agentic / self-serve の bulk migration 手段
  │   - Doc-based / Universal Editor / Document Authoring をサポート
  │
  └─ 位置づけ:
      Importer の後継というより
      "Importer をスケールさせた実行基盤"

        ↓ さらに発展

Experience Catalyst
  ↓
  ├─ import だけではなく migration 全体を扱う agentic レイヤー
  │   - URL inventory
  │   - block / cluster mapping
  │   - import script generation
  │   - bulk import 実行
  │   - upload / preview / validation
  │   - styling / branding / Figma 連携
  │
  ├─ 既存の import infrastructure を再利用
  │   - import.js
  │   - Helix Importer UI の考え方
  │   - Import as a Service
  │
  └─ 位置づけ:
      "Importer を置き換えるだけのツール" ではなく
      "import を含むサイト移行全体の orchestrator"
```

---

### 2. 3世代の関係をひとことで言うと

|段階|主役|何を解決したか|一言でいうと|
|---|---|---|---|
|第1世代|AEM Importer|ページ変換と import.js 作成|**開発者向け importer**|
|第2世代|Bulk Import / IaaS|大量ページを安定実行|**service-backed bulk execution**|
|第3世代|Experience Catalyst|移行全体の自動化・半自動化|**agentic migration orchestrator**|

---

### 3. 誤解しやすいポイント

#### A. `Bulk Import` は完全に独立した別製品名ではない
社内資料上の **Bulk Import** は、文脈によって次のどちらも指します。

1. **AEM Importer の bulk capability**
2. **Import as a Service による service-backed bulk execution**

つまり、`Bulk Import = AEM Importer の次の段階で必要になった実行モデル/運用形態` と捉えるのが一番安全です。

#### B. `Experience Catalyst` は Importer の単純なリネームではない
Experience Catalyst は **import のみ** ではなく、以下まで含みます。

- inventory 作成
- block mapping
- import script 生成
- bulk import 実行
- content upload
- preview / validation
- styling / branding
- Figma 連携や agent skills

したがって、**Importer の発展形を内包しつつ、スコープはもっと広い**です。

#### C. 現場の説明では「階層構造」で話すと伝わりやすい
おすすめの説明順は次です。

1. **Importer** = ページ変換ツール  
2. **Bulk Import / IaaS** = それを大規模実行する基盤  
3. **Experience Catalyst** = それらを使って移行全体を進める agentic レイヤー  

---

### 4. 営業/SE向けの話し方

#### 短く言う版
> AEM Importer が元の import ツールで、Bulk Import はそれを大規模処理できるようにサービス化したものです。Experience Catalyst はその上で、import だけでなく inventory・mapping・styling まで含めて移行全体を自動化する流れです。

#### もう少し正確に言う版
> AEM Importer は import.js を作ってページ変換を試す開発者向けツールとして始まりました。そこから、大量ページをローカルではなくサービス側で処理する Bulk Import / Import as a Service へ発展しました。Experience Catalyst は、その import 基盤を再利用しながら、サイト移行全体を agentic に進める上位レイヤーです。

---

### 5. Universal Editor 前提での読み替え

Universal Editor 前提では、この系譜は次のように読むとわかりやすいです。

- **AEM Importer**  
  既存ソースから **UE 向けの content package / authorable structure** を作るための基礎ツール

- **Bulk Import**  
  UE 向け移行を **多数ページで安定実行** するための実行方式

- **Experience Catalyst**  
  UE 向け移行で必要な **inventory → mapping → import → validation** を、より包括的に支援する仕組み

---

### 6. 今の説明として一番安全な結論

#### 結論
**AEM Importer → Bulk Import → Experience Catalyst** は、  
`単純な製品名変更の一本線` というより、  
**Importer を起点に、scale-out 実行基盤が加わり、さらに agentic orchestration に拡張された系譜** と説明するのが最も正確です。

#### 図式化すると
```text
Importer (tool)
   + scale/runtime
      => Bulk Import / IaaS
   + orchestration/AI/workflow
      => Experience Catalyst
```

---

### 7. 社内向けの一言サマリ

- **Importer** = import を作る・試す
- **Bulk Import** = import を大量実行する
- **Experience Catalyst** = 移行全体を進める

### 2. 外部ページで公開されているか
